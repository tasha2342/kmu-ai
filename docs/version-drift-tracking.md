# 폐쇄망 개발에서의 버전 드리프트 추적

> 작성일 2026-08-20. `kmu-ai` 개발(ys) ↔ 운영(계명대 GPU 서버) 사이의 버전 어긋남을
> 자동으로 잡아내기 위해 도입한 시스템의 배경과 방식.
> 실행 절차는 [`deployment-and-versioning.md`](deployment-and-versioning.md) 를 본다.
> 이 문서는 **왜 이렇게 만들었는가**를 다룬다.

## 1. 문제 — 폐쇄망이 실제로 끊는 것

먼저 흔한 오해부터 정리한다. **폐쇄망이 "버전 식별"을 어렵게 만드는 것은 아니다.**
git 커밋 해시도 도커 이미지 ID도 콘텐츠 주소지정(content addressing)이라, 파일로 옮겨도
값이 그대로 살아남는다. 동일성 확인 자체는 이미 해결된 문제다.

폐쇄망이 끊는 것은 **보고 채널**이다.

일반적인 배포 도구는 둘 중 하나를 전제한다 — 운영을 **관찰할 수 있거나**(ArgoCD 가
클러스터를 조회한다), 운영이 **진실의 원천을 관찰하거나**(Flux 가 git 을 폴링한다).
완전 폐쇄망에서는 **양방향 모두 없다.** 운영은 자기가 무엇을 돌리고 있는지 아무에게도
말할 수 없고, 개발 쪽에서 물어볼 수도 없다.

그래서 상태를 **손으로 들고 나오는 명시적 산출물**로 만들어야 한다. 이 시스템이 하는 일이
정확히 그것이다 — 잃어버린 보고 채널을 사람이 들고 다니는 파일로 복원한다.

## 2. 실제로 겪은 사고

2026-08-19 ~ 20 이틀 사이에 겪은 것들이다. 전부 "어디에 무엇이 올라가 있는지 모른다"는
한 가지 원인에서 나왔다.

| 사고 | 무엇이 안 보였나 | 어떻게 알아냈나 |
| --- | --- | --- |
| 운영 vLLM 이 gemma-4-31B-it 를 못 띄움 | 이미지가 `:latest` 라 어느 빌드인지 알 수 없었다 | 컨테이너에 들어가 `vllm.__version__` 을 직접 찍어 봄 |
| 개발 챗봇이 **모든** 질문에 미응답 | 등록된 `model_id` 는 `gemma-4-31b-it`, 노드가 서빙하는 건 `-awq`. 응답도 의도 분류도 404 로 죽고 있었다 | 컨테이너 로그를 뒤져서 |
| 규정 181건 중 45건만 색인된 채 **8일 방치** | 재색인이 도중에 죽었는데 되돌아보는 잡이 없었다 | 우연히 |
| 운영 `docker-compose.yml` 이 두 브랜치 어디에도 없음 | 서버에서 직접 고쳤고 기록이 없었다 | 파일을 직접 비교해서 |

공통점은 **아무도 몰랐다**는 것이다. 알아채는 데 걸린 시간이 문제였지, 고치는 건 대부분
몇 분이었다.

## 3. AI 협업이 이걸 악화시키는가

정직하게 쓴다. **이 주제를 직접 다룬 연구는 아직 없다.** 아래 한 줄만 인용할 만하다.

DORA 2025 보고서는 AI 도입이 **처리량은 높이지만 안정성 지표(변경 실패율·재작업)는
악화시킨다**고 보고한다. 보고서의 표현은 AI 가 **증폭기**라는 것이다 — 잘 되던 것도,
망가져 있던 것도 함께 키운다.

나머지는 우리 관찰이다.

- **변경 속도가 사람의 검토 속도를 앞선다.** 하루에 커밋 7개가 쌓이는데 그중 무엇이 운영에
  갔는지는 아무도 세지 않았다.
- **세션끼리 작업 공간을 공유하지 않는다.** ys 의 Claude 와 중계 PC 의 Claude 는 서로의
  작업을 볼 방법이 없다. 사람 한 명이 양쪽을 다 기억해야 했다.

한 가지 짚어둘 것: **"담당자 머릿속의 지도가 사라진다"는 문제는 AI 때문에 새로 생긴 것이
아니다.** 구성 관리와 IaC 가 존재하는 이유가 원래 그것이다. AI 로 인한 진짜 변화는
**같은 문제가 예전 대책이 상정한 속도보다 빨리 온다**는 점이다.

## 4. 접근 — 있는 어휘를 쓴다

이 문제 영역에는 이미 확립된 용어가 있다. 새로 만들지 않고 GitOps 어휘를 그대로 쓴다.

| 개념 | 표준 용어 | 이 시스템에서 |
| --- | --- | --- |
| 의도한 상태 ↔ 실제 상태의 어긋남 | **drift** (드리프트) | 그대로 |
| 비교 대상 두 가지 | **desired state** ↔ **live state** | 개발 기록 ↔ 운영 기록 |
| 항목별 판정 | **sync status** (`Synced`/`OutOfSync`) | `DRIFT` / `EXPECTED` |
| 의도된 차이 선언 | **ignore differences** (ArgoCD `ignoreDifferences`, Flux `.spec.ignore`) | `expected_diff` |
| 자동 교정 | **self-heal** | **없다** (아래 참고) |

**중요한 한계를 먼저 밝힌다.** ArgoCD·Flux 는 선언된 매니페스트와 살아 있는 API 객체를
**하나의 조정 루프(reconciliation loop) 안에서** 비교하고 **자동으로 교정**한다.
이 시스템에는 조정 루프가 없다. 두 호스트에 대해 **기록된 사실**을 비교할 뿐이다.

> 얻는 것은 **드리프트 탐지**다. **드리프트 교정도, self-heal 도 아니다.**

## 5. 어떻게 동작하는가

```
수집  version_probe.py 를 대상 호스트에서 실행 → 상태 JSON
기록  version_log.py record  → 비밀값 검사 통과해야 씀
비교  version_log.py report  → DRIFT / EXPECTED / STALE-RULE
알림  세션 시작 훅이 파일만 읽고 요약 출력
```

```
ops/versions/dev.json     ys 의 Claude 만 쓴다
ops/versions/prod.json    중계 PC 의 Claude 만 쓴다 (expected_diff 도 여기)
```

수집기는 **양쪽에서 같은 스크립트**를 돌려 같은 모양의 사실을 만든다. 표준 라이브러리만
쓰고 Python 3.9 에서 돌아야 한다 — 운영은 인터넷이 없어 `pip install` 을 못 하고 3.9.19다.

세션 시작 훅은 **파일만 읽는다. SSH 를 절대 쓰지 않는다.** 매 세션 인증이 발생하면
게이트웨이가 계정을 잠근다. (실제로 3초 간격 폴링으로 차단당한 적이 있다)
실제 수집은 사람이 `/version-check` 를 칠 때만 한다.

### 판정 세 가지

| 판정 | 뜻 |
| --- | --- |
| `DRIFT` | 조치가 필요한 차이 |
| `EXPECTED` | `expected_diff` 에 선언된 차이. 조용히 넘어감 |
| `STALE-RULE` | **선언된 값과 실제가 어긋남.** 규칙이 새 드리프트를 가리고 있다는 신호 |

`STALE-RULE` 이 이 설계의 핵심이다. 억제 규칙은 시간이 지나면 **눈가리개가 된다.**
그래서 `mode: "pin"` 은 값까지 못 박고, 실제가 달라지면 다시 시끄러워진다.
값을 안 적은 `pin` 은 사실상 `ignore` 이므로 그렇다고 경고한다.

## 6. 설계 판단 세 가지

### 6-1. 태그가 아니라 **이미지 ID** 로 비교한다

운영 이미지는 레지스트리를 거치지 않고 `docker save` / `docker load` 로 손으로 나른다.
그래서 태그(`:latest`)로는 아무것도 알 수 없다.

**`docker save`/`load` 가 무엇을 보존하는지 직접 확인했다** (Docker 26.0.0, overlay2):

```
저장 전   Id          = sha256:83b2b6703a62…
          RepoDigests = [alpine@sha256:6baf4358…]
docker save → docker rmi → docker load
저장 후   Id          = sha256:83b2b6703a62…   ← 동일
          RepoDigests = []                     ← 사라짐
```

- **이미지 ID 는 보존된다.** OCI 명세상 이미지 ID 는 **설정(config) JSON 의 SHA-256** 이고,
  그 설정이 모든 레이어의 다이제스트를 참조하므로 **ID 가 같으면 레이어 내용도 같다.**
- **RepoDigest(레지스트리 매니페스트 다이제스트)는 사라진다.** 정확히는 버려지는 게 아니라
  **재직렬화로 무효가 된다** — 내보낼 때 도커가 매니페스트를 OCI 형식으로 다시 쓰기 때문에
  바이트가 달라진다. 매니페스트 다이제스트는 "레지스트리가 저장한 바이트"에 대한 해시라
  그렇다.

여기에 하나 더: **빌드는 기본적으로 재현 가능하지 않다.** 같은 Dockerfile 을 두 번
빌드하면 이미지 ID가 다르게 나온다(확인함). 그래서 개발과 운영의 이미지 ID가 같다는 것은
**각자 빌드한 게 아니라 실제로 같은 산출물을 옮겼다**는 강한 증거가 된다.

컨테이너가 *실제로 돌리는* ID를 기록하므로, `containers.X.image_id != images.Y.id` 이면
**"빌드는 했는데 재시작을 안 한"** 상태도 잡힌다.

> **더 정석적인 방법이 있다.** 폐쇄망 안에 레지스트리를 둘 수 있다면
> `skopeo copy --preserve-digests` / `skopeo sync` 로 매니페스트 다이제스트까지 보존하는
> 것이 낫다. Harbor 복제도 같은 목적이다. 우리는 폐쇄망에 레지스트리를 세울 수 없어
> `docker save` 를 쓴다. 이미지 ID 비교는 **그 제약 아래에서의 차선책**이지 최선이 아니다.

또 하나 정직하게 — **이미지 ID 는 내용의 동일성만 말한다.** "승인된 파이프라인에서
나왔는가"(provenance)는 말해 주지 않는다. 그건 서명·SBOM 의 영역이고, 키리스 서명은
네트워크가 필요해 폐쇄망에서는 별도 설계가 필요하다.

### 6-2. 환경별로 파일을 나눈다

하나로 합치면 두 머신이 같은 파일을 써서 git 충돌이 상시 발생한다. 나누면 **서로 다른
파일만 건드리므로 충돌이 구조적으로 불가능**하다. 이력은 파일 안에 쌓지 않고
`git log -p ops/versions/prod.json` 이 담당한다.

### 6-3. 공개 저장소에 비밀이 들어가지 않게

이 리포는 공개다. 설정값은 화이트리스트에 있는 키만, 세 등급으로만 기록한다.

| 등급 | 기록 | 대상 |
| --- | --- | --- |
| `plain` | 값 그대로 | 이미 템플릿·compose 에 공개된 것 (모델 등록명, 임계값, 불리언) |
| `shape` | 분류 토큰만 (`container:kmu-ai-redis`, `private-ip`, `public-host` 등 7종) | 호스트·URL |
| `presence` | `set` / `unset` | 비밀번호·시크릿·API 키 |

**저엔트로피 값은 해시도 남기지 않는다.** 사설 IP 하나의 SHA-256 은 IPv4 전수
(2³² ≈ 43억)로 수 초 만에 역산된다. SHA-256 이 약해서가 아니라 **원본 공간이 작아서**다.
소금(salt)이 없으면 그 계산은 재사용까지 된다. 규제 관점에서도 해시는
**가명처리이지 익명처리가 아니다**(EDPB·네덜란드 DPA).

`shape` 는 유출이 없으면서 진단력도 있다 — 실제 운영 장애 원인이 `redis.host` 가 엉뚱한
컨테이너를 가리킨 것이었는데, `container:kmu-ai-redis` vs `container:pet-pass-one-ai-redis`
면 한눈에 보인다.

> **용어**: 이 방식은 우리가 만든 게 아니다. 업계에서는 **typed placeholder redaction**
> (유형 표기 마스킹)이라 부르고, Microsoft Presidio 의 `replace` 연산자가
> `<PHONE_NUMBER>` 형태로 같은 일을 한다. "토큰화(tokenization)"라고 부르면 안 된다 —
> 그건 되돌릴 수 있는 매핑 저장소를 뜻하는 다른 개념이다.
>
> **대안**: "값을 공개하지 않으면서 바뀌었는지만 알고 싶다"면 정석은 **HMAC-SHA256 에
> 저장소 밖의 키**를 쓰는 것이다. 단 (a) 키가 새면 다시 2³² 전수로 돌아가고,
> (b) **값마다 다른 소금을 쓰면 안 된다** — 머신 간 동등 비교가 깨진다.
> 우리는 진단력(어떤 컨테이너인지 보이는 것)을 택해 `shape` 로 갔다.

마지막 방어선은 **쓰기 전 검사**다. `record` 는 기록 직전에 정규식으로 훑어 사설 IP·내부
도메인·비밀번호 패턴이 하나라도 걸리면 **쓰기를 거부한다.** 거부되면 우회하지 말고
화이트리스트를 고쳐야 한다.

## 7. 도입 효과

### 첫 실전에서 걸러진 것

운영을 처음 수집했을 때 **DRIFT 가 296건** 떴다. 그중 289건이 파일 단위 노이즈였고,
파 보니 원인이 진짜 문제였다.

**운영 리포의 텍스트 파일이 전부 CRLF였다.** Windows 에서 `tar` 로 옮기며 줄끝이 딸려
갔고, 리포는 LF 로 보관하니 내용이 같아도 286개가 "수정됨"으로 잡혔다. `LICENSE` 는
바이트 내용이 개발과 동일했고 `Dockerfile` 은 `git diff --ignore-all-space` 로 실질
변경이 0줄이었다.

도구 문제가 아니라 **운영 서버의 실제 문제**다 — 운영에서 `git status` 가 못 쓸 상태이고
(진짜 수정이 묻힌다), `git pull` 하면 전 파일이 충돌한다.

비교 범위를 바꿨다: 파일 전체 목록은 조회용으로만 두고 **수정 개수**와 **중요 파일**만
비교한다. 개수를 못 박아 두어 숫자가 변하면 진짜 수정으로 다시 잡힌다.

```
DRIFT 296건 → 4건
```

### 시스템이 잡아낸 것

- **운영이 8커밋 뒤처져 있다.** 그중 규정 재색인 잡(위 §2 의 "8일 방치"를 막으려고 만든
  안전장치)이 정작 운영에 없다.
- **`evidence_max_chars` 가 개발 20000 / 운영 12000.** 같은 질문에 검색 근거가 덜 들어간다.
- **`kmu-chat-gpu.provider` 가 개발 `openai_compatible` / 운영 `local`.** 호출 경로 자체가
  다르다. 의도된 차이인데 선언하지 않아서 시스템이 먼저 물어봤다.
- **`APP_ENV=development` 에 Swagger·OpenAPI 가 켜진 채로 운영이 돌고 있다.**
  이건 드리프트로 안 잡혔다 — **개발과 값이 같아서**다. 시스템의 사각지대이자 실제 문제다.

마지막 항목이 이 도구의 한계를 잘 보여준다. **두 환경을 비교하는 도구는 둘 다 똑같이
틀렸을 때 아무 말도 하지 않는다.** 절대 기준(운영은 `production` 이어야 한다)은 비교가
아니라 별도의 규칙이 필요하다.

## 8. 한계

- **탐지만 하고 교정하지 않는다.** 조정 루프가 없다.
- **양쪽이 똑같이 틀리면 못 잡는다** (위 `APP_ENV` 사례).
- **수집 시점의 사진일 뿐이다.** 운영은 사람이 터널을 열어야 찍을 수 있고, 그사이 서버가
  바뀌면 기록은 낡는다. 48시간 지나면 그렇다고 표시한다.
- **`docker save` 기반이라 provenance 는 없다.** 내용이 같다는 것만 말한다.
- **감시 파일 4개 중 2개(`configs/config.yaml`, `configs/.env`)는 gitignore 라
  `git status` 에 안 잡힌다.** 파일 해시로는 보이지만 의도한 감시는 절반만 동작한다.
