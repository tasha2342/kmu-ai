# 서빙 성능 실측 — H200 ×2 에서 몇 명을 받을 수 있는가

> 2026-08-20, 운영 `kmu-ai-gpu-01` 에서 측정. 스크립트는 [`scripts/loadtest.py`](../scripts/loadtest.py).
> 수치 요약만 필요하면 [`deployment-and-versioning.md` §7](deployment-and-versioning.md#7-모델-서빙-용량-h200-2) 을 보면 된다.
> 이 문서는 **왜 그렇게 쟀고 무엇을 알게 됐는지**를 남긴다.

## 1. 문제 — 용량을 계산만 하고 재 본 적이 없었다

`max-model-len` 을 32,768 → 65,536 으로 올리면서 동시 처리 수를 정리했다. 근거는
vLLM 이 기동하며 로그에 남기는 값이었다.

```
GPU KV cache size: 609,100 tokens
Maximum concurrency for 65,536 tokens per request: 9.29x
```

여기서 "요청당 8,000 토큰이면 76명, 2,000 토큰이면 304명" 같은 표를 만들었다.
산수는 맞다. 그런데 이건 **메모리가 몇 명분 들어가는지**만 말한다.

용량 질문에는 답이 두 개 있다.

| 질문 | 답하는 것 |
| --- | --- |
| 몇 명분이 **들어가나** | KV 캐시 크기 — 로그가 알려준다 |
| 몇 명이 **쾌적하게 쓰나** | TTFT·처리량 — 재 봐야 안다 |

두 번째를 재지 않은 채 "수십 명 동시 사용은 여유롭다"고 써 뒀는데, 이건 첫 번째
답으로 두 번째 질문에 답한 것이다. **메모리가 남는 것과 빠른 것은 다르다.**

## 2. 무엇을 재는가

부하 테스트에서 흔히 "초당 몇 요청"만 보는데, 스트리밍 챗봇에서는 그게 체감과 어긋난다.
사용자는 응답이 다 끝나기를 기다리지 않고 **첫 글자가 언제 뜨는지**를 본다.

| 지표 | 뜻 | 왜 보나 |
| --- | --- | --- |
| **TTFT** | 요청 → 첫 토큰 | 사용자가 "멈췄나?" 하는 구간. 체감의 대부분 |
| **TPOT** | 토큰 간 평균 간격 | 글자가 술술 나오는가 |
| 요청당 tok/s | 한 사람이 느끼는 생성 속도 | 동시성이 오르면 떨어진다 |
| 총 tok/s | 서버 전체 처리량 | 동시성을 올리면 늘어야 한다. **안 늘면 그게 한계** |

동시성을 올리며 **TTFT 는 오르고 총 처리량은 늘다가 꺾이는** 지점을 찾는 게 목표다.

### 두 모드를 나눈 이유

한 번에 재면 어디가 느린지 알 수 없다. 그래서 계층을 갈랐다.

- **`--mode vllm`** — vLLM 의 OpenAI 호환 엔드포인트를 직접 친다.
  검색도 프롬프트 조립도 없는 **모델 서빙 자체**의 성능. GPU 판단은 이 수치로 한다.
- **`--mode chatbot`** — `/v1/chatbot/message` 를 친다. 의도 분류 + 검색 + 응답 생성이
  전부 들어간 **사용자 체감** 성능. 한 턴에 LLM 호출이 두 번 이상 일어난다.

둘의 차이가 곧 앱 계층이 먹는 비용이다. 이 차이가 이번 측정의 핵심 결과가 됐다.

## 3. 어떻게 돌렸나

```bash
# 운영 서버에서
python3 scripts/loadtest.py --mode vllm --max-tokens 256 --out /tmp/lt.json
python3 scripts/loadtest.py --mode chatbot --concurrency 16
```

동시성만큼 스레드를 띄워 동시에 쏘고, SSE 를 흘려 받으며 첫 델타 도착 시각과
델타 개수를 센다. 질문은 실제 사용자 질의와 성격이 비슷한 8개를 돌려 쓴다
(정관·휴학·장학금·기숙사·졸업요건·수강신청·징계·보수규칙) — 길이가 제각각이라
한쪽으로 치우치지 않는다.

제약은 다른 운영 스크립트와 같다. **표준 라이브러리만, Python 3.9 호환, ASCII 출력.**
폐쇄망이라 `pip install` 을 못 하고, plink 가 비ASCII 를 훼손하기 때문이다.
vLLM 컨테이너의 IP·포트는 `docker inspect` 로 자동 탐색하므로 인자로 줄 필요가 없다.

> **개발 서버에서 돌리는 것은 의미가 없다.** ys 에는 H200 이 없다. 이 문서의 수치는
> 전부 운영에서 나온 것이고, 재현하려면 운영에서 돌려야 한다.

## 5. 알게 된 것 — 병목은 GPU 가 아니다

같은 동시성에서 두 모드를 나란히 놓으면 분명해진다.

| 동시성 | 모델만 TTFT | 챗봇 TTFT | 배수 |
| --- | --- | --- | --- |
| 4 | 0.04s | 1.14s | 28배 |
| 8 | 0.05s | 1.72s | 34배 |
| 16 | 0.07s | 2.04s | 29배 |
| 32 | 0.11s | 3.41s | 31배 |

모델은 동시성 128에서도 첫 토큰을 0.3초에 내놓는데, 챗봇을 거치면 32명에서 3.4초다.
**그 차이는 전부 앱 계층에서 생긴다.**

### 어디서 새는지 — 재서 확인했다

처음에는 "LLM 호출이 한 번 더 있고 CPU 임베딩이 끼어 있어서"라고 적었다. **틀렸다.**
`retrieval_logs.latency_ms` 로 검색 구간을 따로 재 보니 임베딩은 병목이 아니었다.

| 구간 | 실측 (부하 중 187건) | TTFT p50(2,040ms) 대비 |
| --- | --- | --- |
| 검색 = 임베딩 + 벡터 검색 | p50 **168ms** / p90 547ms | **8%** |
| 나머지 (LLM 호출) | ~1,870ms | **92%** |

이 `latency_ms` 는 `faq_service.py` 에서 `embed_texts` 를 감싸고 재므로 **임베딩을 포함한**
값이다. 즉 임베딩을 GPU 로 옮겨 0에 수렴시켜도 TTFT 는 2.04초 → 1.87초가 될 뿐이다.

### 진짜 원인 — 보조 LLM 호출의 사고 토큰

그래프는 `condense_query → classify_intent → retrieve → generate` 순이다
(`chat_graph.py` 의 `build_graph`). 앞의 둘은 `complete_text()` 를 쓰는
**비스트리밍 호출**이라 응답을 끝까지 다 받아야 다음으로 넘어간다.

여기에 gemma-4-31b-it 은 **thinking 을 끌 수 없다.** 사고 과정이 먼저 출력 토큰을
소비하고, 그동안 사용자 화면에는 아무것도 뜨지 않는다. 코드에 실측이 남아 있다.

| 노드 | 상한 | 실측 사고 토큰 | 상태 |
| --- | --- | --- | --- |
| `condense_query` | `CONDENSE_MAX_TOKENS` 96 | 93/93 (320으로 올려도 317/317) | **사고만 하다 잘려 항상 빈 문자열** |
| `classify_intent` | `CLASSIFY_MAX_TOKENS` 384 | 0~253 (편차 큼) | 동작하지만 느리다 |

부하 중 TPOT 가 12.9ms 였으니 사고 토큰 253개는 그것만으로 **3.3초**다. 관측된
TTFT 가 정확히 이 범위에 있다.

특히 `condense_query` 는 **매번 왕복을 돌고 결과는 버려진다.** 사고만 하다 상한에
걸려 빈 문자열이 오고, 그러면 원문으로 검색을 이어간다. 동작은 유지되지만
후속 질문의 맥락 복원은 되지 않으면서 지연만 얹는다. 이 사실은 코드 주석에
이미 적혀 있었는데(`CONDENSE_MAX_TOKENS` docstring), **그게 TTFT 를 얼마나 먹는지는
이번에 재기 전까지 몰랐다.**

### 그래서 어디를 손대야 하나

- **GPU 가 아니다.** KV 캐시는 이론상 수백 명분이 남고, 챗봇 부하로는 GPU 사용률이
  100% 근처에도 안 간다.
- **임베딩도 아니다.** TTFT 의 8%다. CUDA 휠로 바꾸면 이미지가 수 GB 불어나고
  API 컨테이너에 GPU 를 물려야 하는데(현재 `docker-compose.yml` 에 GPU 접근이 없다),
  vLLM 이 이미 GPU 당 ~127GB 를 잡고 있어 메모리를 나눠 써야 한다. 8% 를 위해 치를 값이 아니다.
- **보조 LLM 호출이다.** 순서대로 효과가 크다.
  1. `condense_query` — 결과를 못 쓰는데 왕복을 돈다. 후속 질문이 아닐 때 건너뛰거나,
     사고를 덜 하게 프롬프트를 재설계하거나, 이 용도로만 작은 모델을 쓴다.
  2. `classify_intent` — 사고 토큰이 지연을 지배한다. 같은 선택지.
  3. 그다음이 API 워커 수다.

> 임베딩을 GPU 로 옮기는 것이 무의미하다는 뜻은 아니다. **질의 경로에서 무의미한 것이고,**
> 적재 경로는 다르다. 문서 1건 적재가 평균 5.8분(CPU 임베딩)이라 규정 181건 재색인이
> 십수 시간 걸린다. 그 문제를 풀 거라면 근거는 TTFT 가 아니라 적재 시간이어야 한다.

### 남은 의문 — 검색 지연의 꼬리

검색 구간은 p50 168ms 인데 **평균 342ms, 최대 7,189ms** 다. 꼬리가 두껍다.
표본이 부하 테스트 187건뿐이라 원인을 단정하지 않았다. HNSW 탐색인지, 커넥션 풀
대기인지, 임베딩 스레드 경합(`EMBEDDING_TORCH_THREADS=16`)인지 구분하려면
검색 안을 더 쪼개 재야 한다. **아직 안 했다.**

## 6. 고친 것 — 재작성 호출 프리필터 (2026-08-20)

위 분석대로 `condense_query` 를 손봤다. **A/B 로 재서 확인했다.**

### 무엇을 바꿨나

`condense_query` 는 지시어를 실제 대상으로 바꾸는 노드다. 지시어가 없으면 할 일이
없는데, 그 판정까지 LLM 에 맡기고 있었다 (프롬프트의 "이미 완결된 질문이면 원문을
그대로 출력합니다"). 할 일이 없다는 것을 알아내는 데 왕복이 한 번 든 셈이다.

`_needs_condense()` 프리필터를 앞에 뒀다. 지시어가 있거나 아주 짧은 발화면 호출하고,
아니면 건너뛴다. 판정은 문자열 검사라 LLM 이 필요 없다.

### 측정 설계

두 가지를 나눠 재야 한다. 프리필터는 **자기완결적 후속 질문에서만** 작동하기 때문이다.

| 후속 질문 성격 | 예 | 프리필터 | 기대 |
| --- | --- | --- | --- |
| `standalone` | "졸업 요건 알려줘" | 걸러냄 | **빨라져야 한다** |
| `anaphora` | "그럼 기간은 얼마나?" | 통과 | 그대로여야 한다 |

여기에 **1턴을 대조군으로 쓴다.** 1턴에는 대화 이력이 없어 `condense_query` 가
애초에 돌지 않으므로, 1턴이 움직였다면 그만큼은 이 변경이 아니라 환경 노이즈다.

```bash
python3 scripts/loadtest.py --mode chatbot --turns 3 --concurrency 4 \
    --requests-per-worker 3 --followup standalone
```

### 결과 (동시성 4, 셀당 n=12, TTFT p50)

| 구간 | before(`e66700e`) | after(`9995b1f`) | 차이 |
| --- | --- | --- | --- |
| **1턴 — 대조군** | 0.61s | 0.59s | −0.02s |
| **2턴 자기완결** | 0.95s | **0.53s** | **−0.42s (−44%)** |
| **3턴 자기완결** | 0.94s | **0.61s** | **−0.33s (−35%)** |
| 2턴 지시어 | 1.01s | 0.99s | −0.02s |
| 3턴 지시어 | 1.09s | 0.95s | −0.14s |

읽는 법:

- **대조군이 안 움직였다**(−0.02s). 노이즈 바닥이 0.05초 수준이라는 뜻이고,
  아래 −0.42초는 그 위에 있는 실제 차이다.
- **프리필터가 걸리는 경로만 빨라졌다.** 지시어가 든 후속 질문은 그대로다 —
  거기서도 빨라졌다면 오히려 의심해야 한다. 재작성이 안 돌고 있다는 뜻이니까.
- before 에서는 2턴 TTFT(0.95s)가 1턴(0.61s)보다 **0.34초 느렸다.** 대화를 이어간다는
  이유만으로 붙던 페널티다. after 에서는 2턴(0.53s)이 1턴(0.59s)과 같다. **페널티가 사라졌다.**

### 남은 것

`condense_query` 는 여전히 지시어가 든 질문에서 **사고만 하다 상한에 걸려 빈 문자열을
돌려준다.** 이번 변경은 *불필요한 호출을 없앤 것*이지 재작성을 고친 것이 아니다.
지시어가 든 후속 질문의 맥락 복원은 아직 안 된다(위 표의 `anaphora` 행이 그대로인
이유이기도 하다). 고치려면 사고를 덜 하게 하는 프롬프트 재설계나 다른 모델이 필요하다.

`classify_intent` 는 손대지 않았다. TTFT 의 대부분을 여기가 먹지만
(`chatbot_classify` p50 426ms / p90 2,898ms), 이 노드는 `emotion`·`abuse`·`personal`
라우팅의 근거다. 속도를 위해 줄이면 위기 신호 발화가 검색 경로로 새는 식으로 깨진다.
**성능과 맞바꿀 수 있는 대상이 아니다.**


## 7. 측정하며 틀렸던 것

### 총 처리량이 역전돼 보였다

첫 스윕에서 챗봇 동시성 16이 **80.5 tok/s** 로 찍혔다. 동시성 8이 265 tok/s 였으니
처리량이 3분의 1로 떨어진 셈이라 "여기가 한계인가" 싶었다. 재측정하니 **450 tok/s** 였다.

원인은 지표의 정의에 있다.

```
총 tok/s = 모든 요청의 출력 토큰 합 ÷ 파동 전체 시간
```

분모가 **가장 늦게 끝난 요청**까지의 시간이다. 16건 중 한 건만 늦게 끝나도 나머지
15건이 이미 끝나 놀고 있는 시간까지 분모에 들어간다. 스트래글러 하나가 지표를
통째로 끌어내린다.

**한 번 재고 판단하면 안 된다.** 그래서 최종 스윕은 각 동시성을 2회 돌려 안정값을
쓰고, `wall_seconds` 와 `output_tokens` 를 JSON 에 그대로 남겨 나중에 검산할 수 있게 했다.
실패가 0인데 처리량만 떨어졌다면 한계가 아니라 스트래글러를 의심할 것.

### 델타 개수는 토큰 수의 근사다

스크립트는 SSE 델타 하나를 토큰 하나로 센다. vLLM 스트리밍에서는 대체로 맞지만
**정확한 토큰 수는 아니다.** 절대값을 다른 벤치마크와 비교하는 용도로는 쓰지 말고,
**같은 방식으로 잰 값끼리의 비교**(동시성 간, 배포 전후)로만 써야 한다.

### 두 스윕의 조건이 달랐다

동시성 1~16 은 워커당 2요청·워밍업 1회, 32~128 은 워커당 1요청·워밍업 없이 돌렸다.
고동시성에서 시간이 오래 걸려 줄인 것인데, 그래서 **32 이상 구간은 워밍업 효과가
빠져 있다.** 앞 구간이 이미 캐시를 데워 놓은 상태라 실제 영향은 작다고 보지만,
엄밀히 같은 조건은 아니다.

### 챗봇 모드는 응답 길이를 고정할 수 없다

`--max-tokens` 는 vLLM 모드에만 걸린다. 챗봇은 모델이 알아서 끝내므로 응답 길이가
질문마다 다르다(이번 측정에서 평균 109~378토큰). TTFT 는 영향받지 않지만
**총 tok/s 는 응답이 길수록 커 보인다.** 동시성 1의 62.9 와 동시성 4의 203.0 을
그대로 4배 비교하면 안 되는 이유다.

## 8. 다시 재야 할 때

이 수치는 아래가 바뀌면 무효다.

- `max-model-len`, `gpu_memory_utilization`, 텐서 병렬 수 — vLLM 기동 인자
- `evidence_max_chars` 등 프롬프트 예산 (`configs/config.yaml`) — 입력 토큰이 늘면 TTFT 가 는다
- 임베딩 모델·실행 위치 (CPU → GPU)
- 규정·FAQ 코퍼스 규모
- API 워커 수

바꾼 뒤에는 **같은 명령을 그대로 다시 돌려** 표를 갱신할 것. 스크립트가 조건을
인자로 받으므로 재현은 명령 한 줄이다.
