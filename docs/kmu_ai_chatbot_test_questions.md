# kmu-ai 학사 규정 챗봇 — 테스트 문항

계명대 학생이 실제로 물을 만한 것에 kmu-ai가 얼마나 정확히 답하는지 재기 위한 문항 모음입니다.
기계 채점용 골드셋은 [`eval/questions_student.jsonl`](../eval/questions_student.jsonl)이고,
이 문서는 그 사람이 읽는 판본입니다. 두 파일은 같은 소스에서 나옵니다.

**스냅샷 기준** — `resources/regulations/` HWP 181문서. 인덱스 `E181_full` 5,359청크
(표 포함) / `L_full_typed` 4,916청크 (표 제외, 개발머신용). 문항 작성 2026-08-12.

---

## 왜 이 문서가 필요한가

기존 평가(`docs/regulation_rag_eval.md`)의 골드셋 48문항은 **전부 `1-0-x` 법인 규정 8개
문서**를 대상으로 하고, **전부 날짜(24) 아니면 표(24) 추출** 문항입니다.

학생이 실제로 묻는 것 — 휴학 요건, 졸업 학점, 장학금 자격, 기숙사 벌점, 재수강 상한,
징계 절차 — 은 **한 문항도 측정된 적이 없습니다.** "kmu-ai가 실제로 동작하는 정확도"를
알려면 이 공백부터 메워야 합니다.

## 채점 단위를 문서 → 조항으로 바꾼 이유

기존 `Recall@12 0.854`는 **문서 단위** 지표입니다.
[`eval/scoring.py`의 `score_retrieval()`](../eval/scoring.py)은 top-k 안에 `doc_id`가 맞고
`must_retrieve_keywords` 중 **하나라도** 포함된 청크가 있으면 만점을 줍니다.

법인 8문서(1-0-1 = 44청크)에서는 타당했습니다. 그런데 **학칙 `2-0-1`은 단일 문서에
44,810자 / 239청크**입니다. `doc_id=2-0-1, keywords=["휴학"]` 문항은 휴학을 언급한
아무 학칙 청크나 top-12에 들면 만점을 받습니다. 정작 제23조를 못 가져와도 그렇습니다.

그래서 이 골드셋은 **조항 단위**(`recall_article@k`)로 채점합니다. 정답 키는
`gold_articles`의 `(doc_id, article)`이고, 부칙을 제외한 3,967개 키 중 청크 2개 이상으로
쪼개지는 것은 74개(1.9%)뿐이라 사실상 안정적인 청크 ID입니다.

**문서 단위 지표도 나란히 계속 산출합니다.** 과거 리포트의 0.854와 비교할 축을 잃지
않기 위해서입니다. 두 수치는 같은 것을 재지 않으므로 한 슬라이드에서 비교하면 안 됩니다.

## 목표치

**`recall_article@10~12` ≥ 0.90, 가능하면 0.95.**

업계 공통 합격선이 있는 건 아닙니다. 학칙처럼 **틀린 답의 비용이 큰** 서비스라는 점을
고려한 목표치입니다. 조항 단위 지표에 대한 목표이며, 문서 단위 0.854와는 다른 축입니다.

### 왜 205문항인가 — 통계

n=48에서는 Recall 0.90의 95% 신뢰구간이 `[0.778, 0.955]`로 **0.95(`[0.860, 0.988]`)와
구분되지 않습니다.** 목표를 "0.90 이상, 가능하면 0.95"로 잡았다면, 그 둘을 구분할 수
없는 표본으로 잰 수치는 의미가 없습니다.

| n | 0.90을 쟀을 때 CI | 0.95를 쟀을 때 CI | 0.95의 하한이 0.90을 넘는가 |
| --- | --- | --- | --- |
| 48 (기존) | [0.778, 0.955] | [0.860, 0.988] | ✗ |
| 150 | [0.842, 0.938] | [0.898, 0.973] | ✗ (0.898, 아깝게 미달) |
| **205** | [0.848, 0.932] | **[0.913, 0.973]** | **✓** |

n=205에서 0.95를 측정하면 Wilson 하한이 0.913이라 **"0.90 이상"이라는 주장이 자기
신뢰구간을 버팁니다.** 이 표는 `python3 -m eval.stats --plan 0.90 0.95`로 재현됩니다.

## 표 읽는 법

- **✱** 표시 = 정규식으로 채점 불가, LLM 판정 대상 (`judge=true`, 79문항)
- **근거** = 정답이 실제로 적힌 규정 조항. `gold_spans`는 이 조항 원문에서 그대로 떠 왔습니다
  (`eval/gold_builder.py`가 자동으로 채워 전사 오류가 원천 차단됩니다)

## B. LLM 판정이 필요한 문항 (79건, A절 안에 ✱로 표시)

현재 채점기는 `date|number|percent|list|text|unknown` 정규식이 전부입니다. 48문항이 전부
스칼라 추출이라 통했지만, 아래 유형은 정규식으로 채점할 수 없습니다.

| `answer_type` | 건수 | 예 |
| --- | --- | --- |
| `conditional` | 30 | JAN-002 "징계받으면 장학금 못 받아?" → 근신·유기정학은 한 학기, 무기정학은 두 학기 |
| `list_all` | 26 | HYU-001 "휴학 종류에 뭐가 있어?" → 6종을 **전부** 말해야 정답 |
| `abstain` | 20 | NEG-* 전부 |
| `list_any` | 3 | SAE-001 "기숙사는 누가 들어갈 수 있어?" |

**2단 구조 — 결정적 채점이 코어, judge는 보조.** 정규화기를 먼저 돌리고, judge는
(a) `judge=true`이거나 (b) 정규화기가 틀렸다고 본 경우에만 부릅니다.
**정규화기가 맞다고 한 것을 judge가 뒤집지 않습니다.** judge가 죽어도 오늘과 같은
동작으로 degrade합니다.

**판정 모델은 Claude(`claude-opus-5`), Gemma가 아닙니다.** 답을 만든 Gemma가 자기 답을
채점하면 자기일관성을 정확도로 착각하게 됩니다. 전체 1회 실행에 약 $1.6.

**judge는 자기 지식이 아니라 `gold_spans`에 대해 채점합니다.** 이 제약이 없으면 한국
대학 규정을 "아는" judge가 코퍼스에 없는 사실로 오답을 정답 처리하고, 그 순간 검색 품질
측정이 무의미해집니다.

**보정 게이트 — κ ≥ 0.8에서만 채택합니다.** (문항, 예측) 40쌍을 수동 라벨링해
`python3 -m eval.judge --calibrate pairs.jsonl`로 Cohen's κ를 재고, 미달이면 어떤 judge
수치도 신뢰하지 않습니다. κ는 §G에 기록합니다.

재현성은 온도 고정이 아니라 네 가지로 확보합니다 (Opus 5는 `temperature`를 400으로
거부하고 thinking이 기본 on입니다): 디스크 캐시(같은 문항·예측 쌍은 API를 다시 타지
않음) · 루브릭/모델 고정 · JSON 스키마 강제 출력 · 전체 판정 감사 로그(`*_judgments.jsonl`).

## H. 수정 방안

### S0 — 검색 천장부터 측정 (최우선, 생성 없음)

`recall_article@N` 곡선을 N ∈ {5,10,12,20,30,50,100,200}으로 그립니다.
**이 한 수치가 전체 전략을 가릅니다.**

- `recall_article@200 ≥ 0.95` → **순위 문제.** top-100→12 크로스인코더 리랭커가 답이고 통합니다.
- `recall_article@200 < 0.95` → **후보 생성/표현 문제.** 리랭커는 recall@100이 상한이라
  도달 불가. 질의 확장·문서 라우팅 같은 색인/질의 쪽 작업이 필요합니다.

기존 48문항 k-sweep이 `X2_k12` 0.8125 → `X2_k50` 0.8333으로 정체된 것으로 보아
**후자일 가능성이 높습니다.** 후보를 4배 늘려도 +2%p라는 건 정답 청크가 순위가 낮은 게
아니라 후보 풀에 아예 없다는 뜻입니다.

### 개선 실험

| # | 실험 | 계층 | 근거 강도 | 예상 Δ`recall_article@12` |
| --- | --- | --- | --- | --- |
| S1 | `collections.top_k` 5 → 12 | 설정 | **측정됨** (R1 0.854 vs R2 0.792) | +0.06 (프로덕션만) |
| S2 | 문서 제목 라우팅 (버그수정 후) | 질의 | **미측정** — R6은 no-op이었음 | +0.02~0.05 |
| S3 | 질의 확장 동의어 사전 | 질의 | 추정 | +0.03~0.08 |
| S4 | 크로스인코더 리랭커 top-100→12 | 파이프라인 | 추정 | **S0가 상한을 정함** |
| S5 | `section_type` 필터 (부칙·장 감점) | 색인+질의 | 약함 | +0.01~0.03 |
| S7 | 한국어 BM25 (`simple` tsvector 대체) | 색인 | **측정됨(정확도만)** | **+0.00** |

**S1은 프로덕션 한 줄 수정입니다.**
[`chat_graph.py:46`](../app/utils/chat_graph.py)의 `_collection_retrieval_settings()`가
튜닝된 12를 DB 기본값 5로 덮어씁니다. 하네스는 이미 12라 하네스 수치는 안 움직입니다.

**S2는 두 겹의 버그였습니다.** `eval/retriever.py`가 청크의 파일명 키를 `file_name`으로
읽고 있었는데 실제 키는 `source`라, `_title_tokens`가 전부 빈 집합이었습니다. 게다가
한글 파일명에는 띄어쓰기가 없어(`3-4-1장학규정.hwp` → `장학규정`) 어절 토큰 겹침으로는
어차피 아무것도 안 맞습니다. 문자 바이그램 겹침으로 고쳤고, 고친 뒤 실측입니다.

| --- | --- |
| "장학금 성적 기준은?" | `3-4-1` 장학규정 (정확) |
| "복수전공 몇 학점?" | `3-3-5` 복수전공이수규정 (정확) |

| "기숙사 벌점" | **0건** — 규정 어휘는 "생활관" |
| "휴학 기간" | **0건** — 학칙 제목이 그냥 "학칙" |

뒤의 두 줄이 S3(질의 확장)이 필요한 이유를 그대로 보여 줍니다.

**S3 동의어 사전 초안**: 기숙사↔생활관, 자퇴↔퇴학, 학점포기↔이수포기,
성적장학금↔성적우수장학생, 교생↔학교현장실습, 복전↔복수전공, 연체료↔벌금.

**S7은 Recall 예산에 넣지 마세요.** `X3_dense` recall 0.8125 = hybrid 0.8125로 동일합니다.
BM25 융합이 산 것은 정확도(+8%p)이지 recall이 아닙니다. 그럼에도 프로덕션 1순위인 이유는
운영 어휘 검색(`pg_simple`)이 recall **0.0208**로 죽어 있어 지금 사실상 dense 단독으로
돌고 있기 때문입니다. 그 사실을 수치로 드러내려고 `pg_hybrid` 백엔드를 만들었습니다.

**정직한 전망: S1+S2+S3으로 ~0.80 → ~0.90은 현실적입니다. 0.95는 S4 없이 불가능하고,
S4는 S0 결과에 종속됩니다.**

### 시도하지 말 것

기존 리포트 §11에서 측정상 더 나빴던 것들입니다. 셋 다 명백히 좋아 보였지만 나빠졌습니다.

- 래스터 비전 (표 0.625 → 0.292)
- 질량 기반 문서 결정 (날짜 0.917 → 0.792)
- 표 셀 확장 (0.625 → 0.542)

## 부록: 골드 스키마

기존 13필드는 의미 그대로 두고 8개를 추가했습니다. `score_retrieval()`이 요구하는
`doc_id`+`must_retrieve_keywords`와 `score_answer()`가 요구하는
`answer`/`acceptable_answers`/`normalize`가 모두 그대로 있어 **문서 단위 지표가
조항 단위 지표와 나란히 계속 산출됩니다.**

| 신규 필드 | 이유 |
| --- | --- |
| `gold_articles` | 조항 단위 recall의 정답 키 `[{doc_id, article}]` |
| `answer_type` | `exact`/`list_all`/`list_any`/`conditional`/`abstain`. `normalize`는 값의 *형식*, 이건 정답의 *논리 구조* |
| `gold_spans` | 근거 원문 구절. judge의 판정 기준. `gold_builder`가 원문에서 그대로 채움 |
| `required_facts` | `list_all`에서 전부 있어야 하는 항목 |
| `forbidden_facts` | 있으면 환각 |
| `unanswerable_reason` | `NEG-*` 전용: `not_in_corpus`/`personal_data`/`out_of_scope`/`time_sensitive` |
| `category` | ID 접두사. 층화 집계용 |
| `judge` | LLM 판정 필요 여부 |

`python3 -m eval.schema --validate`가 ID 중복, 접두사↔카테고리 일치,
`answer_type`↔`normalize` 정합성, 그리고 **`gold_articles`의 `(doc_id, article)`이
코퍼스에 실재하는지**까지 검사합니다.
