개발 서버와 운영 서버에 실제로 붙어 배포 상태를 수집하고, 무엇이 다른지 보고한다.

세션 시작 훅은 **기록된 파일만** 읽는다(SSH를 쓰지 않는다). 이 명령은 그와 달리 서버에
직접 접속해 기록을 갱신한다.

## 순서

1. **다른 쪽 기록을 먼저 받아온다.**
   ```
   git pull --rebase
   ```

2. **어느 머신에서 도는지 판단한다.** `ops/local.env` 가 있으면 중계 PC, 없으면 ys다.
   (자격증명 파일이라 커밋되지 않으므로 이게 곧 구분자다)

3. **자기 환경을 수집한다.**
   - 중계 PC: `python3 scripts/version_log.py probe --env prod`
     HIWARE 터널이 열려 있어야 한다. `127.0.0.1:13000` 이 닫혀 있으면 스크립트가 즉시
     중단하고 알려 준다. **재시도 루프를 돌리지 말 것** — 3초 간격 폴링으로 계정이 차단된
     전례가 있다. 사용자에게 SFTP/PuTTY 세션을 열어 달라고 하고 기다린다.
     수집은 45초 간격 폴링이라 3~5분 걸린다.
   - ys: `python3 scripts/version_log.py probe --env dev`

   인자로 `dev` 또는 `prod` 가 주어졌으면 그쪽만 수집한다. `report` 만 주어졌으면
   수집을 건너뛰고 4번으로 간다.

4. **전체 비교표를 낸다.**
   ```
   python3 scripts/version_log.py report
   ```

5. **결과를 해석해 사용자에게 전한다.** 숫자만 옮기지 말고 무엇을 해야 하는지 말한다.
   - `DRIFT` — 조치가 필요한 차이다. 어느 커밋을 배포해야 하는지 짚어 준다.
   - `STALE-RULE` — `prod.json` 의 `expected_diff` 에 선언된 값과 실제가 어긋났다.
     누군가 서버를 또 손댔다는 뜻이므로 그냥 넘기지 말고 왜 달라졌는지 확인한다.
   - `EXPECTED` — 의도된 차이. 조용히 넘어간다.

6. **기록을 커밋한다.**
   ```
   python3 scripts/version_log.py commit --env <수집한 환경>
   ```
   `dev.json` 은 ys 만, `prod.json` 은 중계 PC 만 쓴다. 서로 다른 파일만 건드리므로
   충돌이 나지 않는다. **다른 환경의 파일을 고치지 말 것.**

## 주의

- 수집 결과에 자격증명이나 내부 IP 가 들어가면 `record` 가 **쓰기를 거부**한다.
  리포가 공개 저장소라서다. 거부되면 `scripts/version_probe.py` 의 `REDACTION` 을 고쳐야지,
  검사를 우회하면 안 된다.
- 운영 수집이 빈 결과를 돌려주면 실패로 취급한다. HIWARE 는 세션이 조용해지면
  **종료코드 0에 빈 출력**으로 끊어버리기 때문에, 성공처럼 보이는 실패가 흔하다.
  `probe_ok` 가 없으면 기록하지 않는다.
